# 任务就绪检查

1. 读取项目入口与 `ai-workflow.yaml`；检查分支、HEAD、`git status`、相关 diff，保护并行修改和未跟踪文件。先执行 `check-hooks` 或核对 `list` / `status` 内联返回的 `hooks.hook_active`（确认当前会话 SpecLock Hook 已授权并运行），定位任务 ID，查询引擎 `status` / `snapshot`，不以文档勾选代替状态。
2. 核对目标、范围/非目标、验收、需求来源及依赖完成事实，检查环境、设计、接口、数据和验证条件。读取任务卡及关联来源中的待确认项，按下节处理。来源链接未读不算核对，空依赖列表只表示确认无依赖。
3. 按 `tiering` 核对三档人工定档和范围确认；标准短计划不额外审批，完整方案另获批准。既有有效授权不重复索要。
4. 列出实际可执行的检查和人工操作。关键缺项未解决时，只继续调查或推进独立、已授权且已就绪的其他任务。
5. 新任务优先用 CLI `prepare`（自动从 `ai-workflow.yaml` 派生必读基线和检查计划并一步绑定会话，并内联返回 `hooks` 状态；仅在 `hooks.hook_active` 为 `true` 且当前会话缺少原生单选工具需降级聊天回复时附加 `--request-tier`）。发起定档或方案批准前务必核对 `hooks.hook_active`：若为 `false`，禁止调用原生单选卡片或让用户手打口令，应先向用户报告未检测到已授权钩子并**写明宿主重新授权步骤**（如 Codex 的 Settings → Hooks 或 `/hooks` 重新信任并启用 `workflow-core@speclock`、Claude Code 在 `/hooks` 确认启用 `workflow-core` 钩子、Cursor 确认已启用插件与 `hooks/cursor.json`，特别是升级插件后需重新信任，然后新开/重启会话），**不得省略授权指引只给终端命令**，同时把交互终端 `confirm-tier` / `approve-proposal` 作为备选一并给出；若为 `null`（`ENGINE_HOOK_SESSION_UNKNOWN`），传入真实 `--session`（Codex 为 `CODEX_THREAD_ID`，Claude Code 为 `SessionStart` 注入的 `session_id`/`CLAUDE_SESSION_ID`，Cursor 为 `conversation_id`/`CURSOR_CONVERSATION_ID`）重新核对；仅在 `hooks.hook_active` 为 `true` 时按 `workflow` 发起确认（Claude Code 使用 `AskUserQuestion` 或 `ExitPlanMode`；Codex 可使用 `request_user_input` 或 `request_user_input_async`，使用 `request_user_input_async` 时须调用 `clock.sleep` 保持回合等待点击，不要立即结束回合关闭弹窗，并在收到回执后用 `status` 核实；Cursor 或缺少原生点选时使用 `request-confirmation` 聊天确认；完整档在发起方案批准卡片前须先运行 `render-md --task <任务ID> --save` 并在聊天正文完整展开方案内容与审阅稿路径，切勿压缩为简短摘要）。执行后留意输出中的 `reconcile` 字段，若有已被自动关闭的未开工旧任务或已开工冲突须如实转告用户。人工定档（及完整档批准）完成后，优先用 CLI `begin --executor ... --session ... [--tdd-json ...]` 一步批量读取全部必读基线正文、登记 SHA-256 回执、进入 `implementing` 并获取 `progress` 投影。若整批超限（`BASELINE_BATCH_LIMIT`）或宿主工具截断输出，改用 `read-baseline --path` 分批重读后再 `start`。回执逐份记录路径、内容摘要、读取字节、执行者和轮次；缺失、失败、截断、冲突未处理不能通过。引用只按适用范围展开，不无限递归。Agent 必须实际使用正文。
6. 就绪后确认状态已进入 `implementing`；命令与参数先看实际 CLI `--help`，通用入口见 `workflow`。

## 待确认项的追问与恢复

1. 任务卡处于 `协作状态：待确认`、存在未决 `- 待确认：` / `Qxx` 项或存在关键需求/设计/契约歧义时，直接按 `clarify`（`grill-me` 式深度澄清）推进，不靠猜测开工。
2. 提问前先查任务卡、需求、设计、契约、源码与已确认决定；能从权威来源查清的按依据补齐，只把真正会改变实施或验收且需人决定的分歧整理为决策树。环境、权限或上游交付缺失时，说明需要补齐的实际条件。
3. 开工前把已知会阻止本任务实施的未决问题登记为 `dependencies` 中的 `{"id":"Q01","status":"pending"}`，使用已有问题编号，保留其他依赖。新任务随可用的真实详情登记，已有任务用 `update-task`。材料不足以创建任务时，在会话保留问题及依据，等材料齐备后再登记。
4. 沿决策树按依赖顺序逐枝追问（每轮聚焦 1 个决策点或同一分支内紧密相关的 1～2 项），每项写明影响范围、候选方案与推荐答案及依据；无法由当前用户拍板的外部阻塞保持待确认并继续澄清其他独立分支。使用宿主可用的原生提问工具或聊天提问，且**严禁携带 `workflow-confirm:` 标记**。等待答复期间暂停依赖该决定的改动，超时、沉默或「继续」都不能代替具体结论。
5. 收到明确答复后，保留原问题编号，按 `clarify` 同步回写模块卡与需求说明（含协作状态更新），并用 `update-task` 将已解决的 `dependencies` 更新为 `done`（保留其余依赖）及同步受影响的目标、范围、验收或计划。读取最新 `status` 并复核就绪条件；若控制摘要变化导致授权或基线回执失效，按现有规则补齐。满足条件后在同一会话继续，无需用户再发一次「执行」。仍缺决定或条件时，只暂停受影响的工作并说明恢复条件。

## 检查要点

- **任务卡回写**：有明确对应的模块卡时，在任务登记或定档前补入 `card: {"path":"仓库相对路径","id":"卡内标题 ID"}`。确认模块卡位于 `docs.cards_dir` 内，标题和状态字段唯一。没有明确对应关系时不猜测目标。
- **文档基线与执行基线分开**：前者是必读规范，后者是修改前测试/分析结果。文档改动先跑相关文档检查；代码任务先跑相关测试和分析，记录既有失败及同环境证据。
- **UI/设计**：核对主稿、页面/节点、状态、素材、共享 UI；仅文字/结构已读不能声明视觉已核对。
- **接口/数据**：核对契约版本、负责人、Mock/真实联调阶段、可重建测试数据；关键契约不明不猜，见 `api-contract`。
- **平台**：按 `platforms.*`，范围外写“按约定未执行”；未配置时先确认可验证主平台，不凭空许诺全平台通过。
- **恢复**：新 Agent 必须重读适用基线，旧 Agent 在内容变化时重读；有效方案不因换执行者重批。核对任务、当前轮次和活动主执行者，运行中命令先查真实进程；未知活动不猜阻塞。

不在当前任务中途自行补配置或降低要求；缺关键批准、基线或安全测试条件时报告影响与恢复条件。
